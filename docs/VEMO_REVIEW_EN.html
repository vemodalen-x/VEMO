▣ Headline

The design intent scored 8.6 in the iteration log. This review audits the shipped code with a skeptic's eye and is deliberately stricter: VEMO v1.0 had the right architecture but three enforcement mechanisms were holed — a parser bug left the R2 judge gate silently dead, the risk tier was self-declared (an agent could downgrade R2→R0 to skip gates), and degradation was fail-open. A framework whose "hard gates" don't actually fire is back to Wildpanda's problem in a nicer costume. v1.1 repairs all three (verified, below) and lifts the shipped score to 8.3. The remaining gap to the design intent is honest: Windows hook portability and a real eval runner.

↻ Updates since this review (v1.2 → v1.4)

This review audits v1.0→v1.1; the framework has since continued. v1.2: a full-auto/unattended mode (records every decision; safety + judge unchanged; explicit-command-only, TTL-bounded). v1.3 (from Fable 5 / Mythos analysis — see FABLE5_MYTHOS_OPTIMIZATION.md): run-budget stop rules (hard-stop a runaway when unattended, advisory when attended), a frontier capability tier + frontier model routing, and a judge evidence-completeness check (guards the documented 20× undercount). v1.4: a unified vemo CLI, per-stack presets, and Diátaxis docs — the usability/understandability/generalization round. 1 What VEMO is (English overview)

VEMO (Velocity-first, Enforced, Model-aware Orchestration) is a drop-in governance framework for AI coding agents, rebuilt from Wildpanda + 2026 best practices. Its thesis: keep Wildpanda's philosophy, but pay for governance with mechanism instead of developer speed.

Five shifts vs. Wildpanda

#WildpandaVEMO
1Gates are prose the model may ignoreMechanically enforced (hooks + CI backstop) — "can't hallucinate"[1]
2Front-load ~20 specs each sessionJIT-load only what a task needs (manifest)[5]
3One ceremony level for everythingRisk-tiered: R0 fast / R1 standard / R2 critical
4Ceremony is a constantScales with model capability (capability.tier)[2]
5Agent self-reports a gate passIndependent judge subagent verifies high-risk gates

Architecture (four layers + one new enforcement layer)

Entry
AGENTS.md — a ~50-line router (vs Wildpanda's 215). Loads config + the always-on safety spec, then JIT-loads the rest.
Config
vemo.config.yaml — the single instance file: capability.tier, model_routing, risk_tiers, enforcement.
Specs
specs/ — slim, JIT-loaded (task / safety / verify / concurrency / coding) + _manifest.yaml (progressive disclosure).
Enforce
enforcement/ — the layer Wildpanda lacked: Claude Code hooks (client-side), git pre-commit + CI (server-side authority), and a stdlib-Python validator that parses machine-readable task front-matter.
Agents
agents/governance-judge.md — an independent verifier (Opus) prompted to refute "done"; eval/ — a conformance harness.

The velocity engine: risk tiers

R0 trivial · plan-inline → implement → done· R1 standard · plan → implement → verify· R2 critical · plan → review → implement → verify(+judge) → procedure

A typo and a schema migration do not deserve the same process. Default to the lowest tier that fits — that is where the developer-acceleration comes from.

2 Critical review (adversarial auditor lens)

I assume the worst: a lazy or adversarial agent, a missing tool, a tired developer at 6pm. The question is not "is the design nice?" but "what actually fires, and what can be bypassed?"

⚙ Demonstrated defect — the R2 judge gate was silently dead in v1.0

VEMO v1.0 used a hand-rolled stdlib YAML reader. Run against a real task file it collapsed nested mappings to [], so judge.verdict was unreadable — the gate that is supposed to make the judge mandatory could never see a verdict:

# v1.0 parser on tasks/T-...-demo.md
parsed keys: [... 'acceptance', 'status', 'build_exit', ... 'judge', 'required', 'verdict' ...]
acceptance value -> []      # should be a mapping
judge value      -> []      # judge.verdict NEVER readable → R2 judge gate is dead

This is the cardinal sin a VEMO review must catch: a "hard gate" that doesn't fire is exactly the failure VEMO was built to fix. Found, then fixed in v1.1 (§3).

Findings

IDSeverityFindingv1.1
F1HighParser correctness: nested front-matter collapsed → judge.verdict unreadable → R2 judge gate dead. (demonstrated above)fixed
F2HighSelf-classification loophole: risk tier was agent-declared. A lazy/adversarial agent marks an R2 change "R0" and skips review + judge. The trust problem VEMO criticized, reintroduced.fixed
F3HighJudge not mechanically required: nothing forced the judge subagent to actually run on R2 — the agent could simply not invoke it.fixed
F4MedFail-open degradation: degrade_gracefully:true meant a missing python3 silently disabled the scope guard (logs, allows). A missing guard treated as a safe guard.fixed
F5MedWindows portability: hooks are bash + python3; on Windows they need git-bash/WSL — ironically weaker than Wildpanda's PowerShell in the enforcement path.partial
F6Loweval/ is aspirational: ships scenarios + metric definitions but no agent-running harness — measurability is promised, not yet executable.roadmap
F7LowNo config validation: a typo in vemo.config.yaml (e.g. tier: hihg) silently falls back.fixed
F8InherentIrreducible trust core: the session-start bootstrap ("load config + manifest") is still advisory prose. Enforcement shrinks the trust surface; it cannot remove the first step where the agent must choose to read.accepted
◎ What holds up well
Philosophy & problem framing, the risk-tiered velocity model, JIT context, capability.tier+routing, and the kept-from-Wildpanda concurrency/takeover model are all genuinely strong and survive the audit unchanged. The weaknesses were concentrated in the correctness and bypass-resistance of the enforcement mechanisms — which is precisely where a governance framework must be unimpeachable.

4 Optimization round → VEMO v1.1 (verified)

Each fix maps to a finding and is backed by a run, not a claim. v1.1 makes the enforcement layer correct and non-bypassable.

FixFindingWhat changed
Correct nested parserF1New indentation-based YAML-subset parser in task_state.py; judge.verdict is readable again. Also caught a follow-on bug: inline lists with trailing #comments were parsed as character strings (fixed via rfind("]")).
Diff-derived risk tierF2tier-required computes the required tier from the staged paths; the CI backstop blocks a self-downgrade (declared < required).
Mandatory R2 judgeF3CI blocks an R2 push unless judge.verdict == pass. The judge can no longer be skipped by not calling it.
Fail-closed guardsF4degrade_gracefully now defaults false; scope/command/secret guards block when they cannot verify.
doctor + nested getF7Config + task front-matter validation; dotted field reads enable the gates above.
✔ Verification — the fixes actually work (live runs)
# F1 — nested parsing restored
acceptance -> {'status': 'not_run', 'build_exit': None, ...}
acceptance.status -> not_run        judge.verdict -> None     # readable now

# F2 — required tier computed from PATHS (not the agent's word)
README.md       -> R0     src/app/x.ts   -> R1
src/core/k.cpp  -> R2     mixed(R0+R2)   -> R2   # takes the highest
# → CI blocks if a task declaring R0 stages src/core/** (downgrade refused)

# F4 — scope guard still blocks out-of-scope edits
edit src/auth/login.ts (out of task scope) -> hook exit 2  (BLOCKED)
edit src/fusion/core.ts (in scope)         -> hook exit 0  (allowed)

# F7 — config/task sanity
VEMO doctor: OK — no issues

Net effect: the three High-severity findings (F1–F3) and one Medium (F4) are closed and demonstrated; the enforcement layer now does what the design promised — it fires, and it cannot be talked out of firing.

5 Remaining limitations & roadmap (honest)

ItemSevPlan
Windows hook runner (F5)MedShip a pure-Python hook dispatcher (or Node) so hooks run natively on Windows without git-bash. Core logic is already pure-Python.
Executable eval harness (F6)LowA runner that drives an agent through each scenario and asserts the gate outcome from telemetry + front-matter; report per-model-tier metrics so relaxing a tier on a stronger model is a data decision.
Tamper-evidenceLowCI verifies the hook/CI config + validator hashes are intact, so "disable the guard" is itself detectable.
Irreducible bootstrap (F8)InherentCannot be hooked away (the agent must choose to read step 1). Mitigation: keep it one line; make everything after it mechanical. State the limit honestly rather than pretend.
◎ Closing

The discipline this review models is the point: a governance framework earns trust only by being audited adversarially against its own promises. VEMO's promise is "gates that fire." v1.0 made that promise in prose-free mechanism but didn't fully keep it; v1.1 does, and says clearly where it still falls short. That loop — build, attack, measure, fix, disclose — is itself the most important best practice, and it is the one VEMO bakes into eval/ so it keeps happening as models get stronger.

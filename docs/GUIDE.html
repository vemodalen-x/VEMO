VEMO Guide

How to use the framework, and how it's built — governance for AI coding agents that accelerates developers: mechanism over prose, ceremony that scales to risk and model strength.

Start vemo init --preset <stack> See state vemo status Learn vemo explain <topic> License MIT

0 What VEMO is, in 5 ideas

Drop it into any repo. The rules that matter become mechanical (hooks/CI), the advice stays in slim specs loaded just-in-time, and how much process you pay scales to the change's blast radius and your model's strength.

  1. Mechanism over prose — scope, destructive-cmd, secrets, verify-before-push are enforced by code, not goodwill.
  2. Ceremony scales two ways — by risk (R0→R2) and by model (frontier→low).
  3. The repo is the memory — durable state in tasks/<id>.md front-matter (machine-readable).
  4. Verify, don't trust — an independent judge flips high-risk gates, not the worker's self-report.
  5. Bounded autonomy — unattended runs get stop rules + a full decision record.
The one-line mental model

VEMO = a thin router + slim specs + a mechanical enforcement layer + an independent judge. Everything else (risk tiers, capability tiers, auto mode, run budgets) is just how hard each of those leans in for a given change and model.

Where autonomy fits
In auto mode the human-approval pauses (R2 plan review, push confirmation, …) are replaced by auto-decide + record — but every red/blue gate above still fires unchanged, and a run-budget gate (not shown) hard-stops a runaway when no human is watching.

3 Enforcement — defense in depth

Two walls, so a gate never depends on the agent's goodwill. The client-side hook gives fast feedback inside the agent loop; the server-side CI is the authority that --no-verify can't slip past.

Why two walls
The hook is fast but client-side (could be absent on a hookless agent). CI is the authoritative backstop — it re-runs server-side, so even a human or a misconfigured agent is caught. Belt and suspenders.
Reads machine-readable state
Both walls call validators/task_state.py, which parses the task file's YAML front-matter (state · scope_in · acceptance · judge verdict). Deterministic — no guessing from prose.

5 Usage

Start without thinking (presets + one command); think when you need to (everything is a documented knob).

Install & initialize

# 1) drop VEMO into your repo
cp -r VEMO/{AGENTS.md,vemo.config.yaml,specs,enforcement,agents,tasks,bin,presets} your-repo/ && cd your-repo
# 2) one command: installs hooks + git pre-commit, preconfigures build/test for your stack
python3 bin/vemo init --preset python      # or: node | cpp | docs   (--dry-run to preview)
# 3) add bin to PATH so you can just type `vemo`
export PATH="$PWD/bin:$PATH"

Do work

# start a task; set its scope. Out-of-scope edits are then blocked automatically.
cp tasks/_TASK_TEMPLATE.md tasks/T-myfeature.md
# edit front-matter:  scope_in: ["src/feature/**"]   risk: R1
vemo status                 # tier / enforcement / budget / auto / active task
vemo explain gates          # what's enforced vs advised

Modes (turn on only what you need)

ModeWhat it gives youHow
Risk tiersLess process for low-risk work (R0 fast path)auto-derived from paths; set globs in risk_tiers
Capability tierLess hand-holding as the model gets strongercapability.tier: frontier|high|medium|low
Auto modeUnattended runs: decide + record instead of askingvemo auto on (OFF by default, TTL-bounded)
Run budgetStop rules so a long run can't "run until cut off"run_budget in config; hard-stops only when unattended
When a gate blocks you
It's not negotiable — fix the cause, don't retry verbatim or --no-verify around it (CI re-checks). Out of scope? Either add the file to the task's scope_in via a replan, or it belongs to a different task.

6 The vemo CLI

One verb-based entry point. Run vemo with no args for the map, or vemo explain <topic> to learn a concept in one sentence.

CommandDoes
vemo init [--preset python|node|cpp|docs] [--dry-run]Set up VEMO in this repo: apply a stack preset, create tasks/, install hooks + git pre-commit.
vemo statusPlain-language dashboard: version, capability tier, enforcement on/off, run budget, auto mode, active task.
vemo doctorHealth check: config + task front-matter sanity, hooks installed, tools present.
vemo explain <topic>One-sentence explainer: tiers · gates · auto · budget · judge · capability · presets.
vemo auto on|off|statusFull-auto (unattended) mode. on --max-tier R2 --allow-r2 to raise the ceiling.
vemo budget status|resetInspect / reset the run-budget counter (calls · files · wall-clock).
vemo tier <paths…>Show the required risk tier for the given paths (R0/R1/R2).
vemo check <path>Is a path inside the active task's scope_in? (in-scope / out-of-scope)

Design Iteration Log · 3-Lens Scoring → Rebuild

VEMO 设计迭代日志 以 Wildpanda 为起点,循环 3 次、每次切换工程师视角打分,收敛出一套「给开发者加速」的治理框架

基线 Wildpanda 6.1/10 终值 VEMO 8.6/10 北极星 time-to-correct-commit ↓ 产物 VEMO/ 可落地框架

M 方法:为什么是「3 视角循环」

单一视角会自我锚定。我让三类工程师轮流上场,各自带着不同的评分坐标系与偏见来挑刺;每一轮的批评直接转化为对设计的改动,下一轮换人复盘。三轮之后,设计在三套坐标系下都站得住,才收敛为 VEMO。

🪝

「我用原语思考」
CLAUDE.md/AGENTS.md · MCP · skills · subagents · hooks · plan mode。信条:把约束放进正确的层,确定性机制永远胜过提示词。[1]

② 迭代二 · OpenAI / Spec-Kit + 开发者体验视角

⚡

「速度即产品」
给百万开发者发 spec-driven 工具。死磕 time-to-first-correct-commit、摩擦、模型路由、评测。[2]

③ 迭代三 · Staff 工程师 / SRE(对抗者)视角

🛡️
Perspective 3 / production adversary
「我专找它怎么死」
见过太多框架死在生产。我攻击:hook 怎么绕?爆炸半径多大?累瘫的人还会用吗?什么会漂移?judge 多烧钱?
⛔ 这个镜头用对抗坐标系重评「v2」(分数故意先回落,暴露缺口)
客户端 hook 可被 --no-verify 绕过;judge 每次 R1 都跑会很烧钱也拖慢;一个 config 虽好但若复杂也劝退;PowerShell 只能 Windows(本机是 Linux);规范仍可能与代码漂移;工具缺失时若静默放行=假安全。

✔ 本轮落地到 VEMO 的改动
  • 纵深防御:hook 给快反馈,enforcement/ci/pre-commit 做服务端权威,二者缺一仍有兜底。
  • 优雅降级:degrade_gracefully — 工具缺失时「响亮告警 + 记日志」,绝不静默放行。
  • 成本守门:judge 仅按 risk tier 触发;high-tier 下 R1 自验证,不滥用大模型。
  • 可移植引导 + 遥测 + 漂移检测,以及每个 spec 的反膨胀行数上限。

保留 / 改造 / 新增 / 砍掉(相对 Wildpanda)

✓ 保留

  • 证据高于断言 · 库即事实源
  • 多会话 chat_id/心跳/接管
  • template/instance/runtime 三分
  • plan-first · PR-only · 人在环
  • 产物溯源(coding §provenance)

↻ 改造

  • 20 步全读 → JIT manifest
  • prose 硬门 → hooks/CI 机制门
  • 统一重流程 → R0/R1/R2 分层
  • 硬编码 opus → capability.tier+路由
  • 自报门通过 → judge 独立翻牌

+ 新增

  • enforcement/ 机制层(本质增量)
  • 机器可读任务 front-matter
  • eval/ 一致性评测 + 遥测
  • governance-judge 独立验证者
  • 跨平台 install.sh

− 砍掉/降级

  • 「Agents loading/loaded」口令
  • 重叠多重 prose 门(并入机制)
  • 引用未落地原语的触发器
  • 小任务的强制重流程
  • PowerShell-only 路径
◎ 一句话
Wildpanda 想清了「治什么」;VEMO 把它做成了机制保证、数据可证、且随模型变强而自动变轻的东西。治理的终局不是规则更多,而是恰到好处地少——而「少」的前提,是把不可让步的那几条交给机器,而不是交给运气。
